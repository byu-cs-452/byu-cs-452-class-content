How connections are stored

Paper A cites paper B. Where does that fact actually live on disk, in a SQL database and in a graph database? And what do 1,000,000 of them cost?

1. In SQL, a connection is a row with two ids

A relational database has no "connection" object. A many-to-many connection is a row in a junction table that holds the id of each side. The database finds the other side by looking that id up, usually in a B-tree index.

2. In a graph database, a connection is a record with pointers

Neo4j (Community edition's default record-aligned format) stores every node and every relationship as a fixed-size record in its own file. Because every record is the same size, a record's id is simply its slot number: relationship 1,000 starts at byte 1,000 × 34. Finding it takes arithmetic, not a search.

3. What ids do they use?

Most SQL tables use an auto-incrementing integer. Neo4j also hands out integer ids, but they mean something different.

Id schemeWhat it isSizeGotcha
SQL BIGINT identity / serialA counter: 1, 2, 3, … Stored in the row and in every index entry.8 BGuessable; needs one central counter.
SQL UUID128-bit random id, generated anywhere without coordination.16 BTwice the bytes in every row and index; random order spreads B-tree inserts across the whole index.
Neo4j internal idThe record's slot number in the store file. Byte offset = id × record size.~35 bitsReused after deletes. Never put it in a URL or another system. Neo4j 5 exposes it as elementId().
Your own key on a nodeA property such as paperId or a UUID, with an index on it.property + indexThis is the id the outside world should use; the slot id is for the engine.

Other graph databases differ. Amazon Neptune, for example, uses string ids that you supply or it generates. The idea is the same everywhere, though: the engine connects records with its own internal addresses, and you keep a stable business key for the outside world.

Where the bytes go

PostgreSQL row: 44 B

  • 24 B row header (23, padded). It holds the transaction ids that let readers and writers work at the same time (MVCC).
  • 16 B data: two 8-byte ids.
  • 4 B pointer to the row in its page.

Then each index stores the ids again, plus a pointer back to the row. The cited_id index is small (9.5 B) because Postgres de-duplicates repeated keys: each paper is cited ~10 times.

Neo4j relationship: 34 B

  • Both node ids, the type, four chain pointers and a property pointer, all in one record.
  • No separate index: the node record points to its first relationship, and the chain does the rest.
  • Records are aligned to 8 KB pages (240 per page), so 1,000,000 records = 4,167 pages = 34,136,064 bytes, exactly what we measured.
Fair-comparison notes. These are bare connections with no properties. Give each citation a year and Neo4j adds a record in its property store, while Postgres just widens the row. Postgres with 4-byte INT ids shrinks too. Neo4j Enterprise also has a newer block format that packs a node and its relationships into the same block. The big picture holds anyway: a graph database spends its bytes on pointers, and a relational database spends them on ids plus indexes to find those ids.

5. What it costs to follow a connection

Storage is only half the story. The real difference shows up when you follow connections several hops deep: "papers cited by papers cited by paper 42".

-- SQL: one join (index search) per hop
SELECT count(*)
FROM cites c1
JOIN cites c2 ON c2.citing_id = c1.cited_id
JOIN cites c3 ON c3.citing_id = c2.cited_id
WHERE c1.citing_id = 42;
// Cypher: follow pointers
MATCH (p:Paper {paperId: 42})
      -[:CITES*3]->(x)
RETURN count(x);
  • SQL: every hop searches a B-tree, O(log n) per lookup. With 1M rows that's about 3–4 page reads per lookup, repeated for every row at every hop. The cost grows with the size of the whole table.
  • Graph: every hop reads a pointer and jumps to id × 34, O(1) per relationship. The cost grows with the part of the graph you actually touch, not the total size.
  • For one hop, or for "count citations per year across everything", SQL is excellent and often faster. For deep or variable-length paths (*1..6), shortest paths and recommendations, the graph layout wins.

6. Questions to think about

  1. Neo4j didn't need a second index for "who cites paper 7?". Which fields in the 34-byte record make that possible?
  2. Why is the Postgres primary key index almost as big as the table itself?
  3. Why would it be a bug to store a Neo4j internal id in another database or in a URL?
  4. Switching from BIGINT to UUID added about 50 MB. Where did those bytes go?
  5. Your Neo4j project's data: would it be smaller or larger in Postgres? What would the junction tables be?
