How Redis Scales

Redis keeps everything in RAM on one machine, and that one machine gets you surprisingly far. When it stops being enough, Redis Cluster splits the keys across several machines using 16,384 hash slots. This page shows where a key lives, what happens when servers are added, removed or die, and what Redis does (and doesn't do) about balancing load.

1 · Scale up first

Most Redis setups are one primary, plus a copy

Before anyone shards Redis, they usually make the one machine bigger and add a backup. Scaling up is boring, and boring is good: no slot maps, no redirects and no rules about which keys can be used together.

More memory

Buy a bigger machine. Cloud providers sell Redis nodes with hundreds of GB of RAM, and most caches are far smaller than that.

More reads

Add replicas: copies that follow the primary and answer reads. Writes still go to the one primary.

Survive a crash

Redis Sentinel (or your cloud provider) watches the primary and promotes a replica if it dies. That gives you availability, not more capacity: every node holds all the data.

When one machine stops being enough

  • The data won't fit in the RAM of the biggest node you are willing to pay for.
  • Writes max out one CPU core. Redis runs commands one at a time on a single main thread. Since Redis 6, extra threads can handle network I/O, but commands still run one at a time. A 64-core box doesn't give you 64× the writes; several primaries do.
  • You want to grow in small steps instead of jumping to the next machine size.

So how many people actually cluster?

We looked for a percentage and couldn't find a trustworthy one. Redis, AWS, Azure and Google don't publish the split between clustered and single-primary deployments, and the numbers floating around blogs have no sources.

What we can say: Azure Managed Redis now creates every new cache in clustered mode, but with one shard, so it is "clustered" on paper while still living on one primary until it grows. Redis's own write-up still recommends standalone mode for its simplicity, compatibility and lower cost.

Our best guess, not a statistic: most deployments are one primary with replicas, and clusters show up when data or write volume outgrows one machine.

2 · Where a key lives

Every key belongs to one of 16,384 slots

Redis Cluster never hashes a key straight to a server. It hashes the key to a slot with CRC16(key) mod 16384, and a table says which server owns each slot. Moving data means moving slots, not rehashing keys. If the key contains {…}, only the part inside the braces is hashed. That's a hash tag, and it's how you keep related keys together.

Why hash tags matter

A command that touches several keys (MGET, MULTI/EXEC, a Lua script) only works in a cluster if every key is in the same slot. Otherwise you get CROSSSLOT Keys in request don't hash to the same slot. Give the keys a shared tag ({user42}:cart, {user42}:profile) and they always land together.

The fine print

  • Only the first { and the next } count.
  • Empty braces don't count: foo{}{bar} hashes the whole key.
  • The flip side: everything with one tag lives on one node. Tag a million keys {everything} and you've rebuilt a single server.

    4 · MOVED and ASK

    How clients find the right node, even mid-move

    There is no proxy in front of a Redis Cluster. Clients keep their own copy of the slot table and talk straight to the right node. When their copy is out of date, the node tells them where to go.

    MOVED: "that slot lives somewhere else now"

    # client's map still says slot 4321 is on A
client → A: GET user:7
A → client: -MOVED 4321 10.0.0.12:6379
# client updates its map: 4321 → B, retries
client → B: GET user:7
B → client: "Ada"

    Permanent. The client fixes its slot table, and every later request for slot 4321 goes straight to B.

    ASK: "this one key already moved, ask B just this once"

    # slot 4321 is half-moved: A MIGRATING → B IMPORTING
client → A: GET user:7
A → client: -ASK 4321 10.0.0.12:6379
client → B: ASKING
client → B: GET user:7
B → client: "Ada"
# next request for slot 4321 still goes to A first

    One-time. During a move, A still answers for keys it has. For keys already sent to B, it says ASK. Once the whole slot is moved, A starts answering MOVED.

    5 · Load balancing

    Redis balances slots, not traffic

    CRC16 scatters keys evenly across slots, so if slots are evenly spread, data is roughly even. But Redis Cluster has no idea which keys are busy. Balancing work is mostly your job.

    JobDoes Redis Cluster do it?How
    Spread keys over slotsautomaticCRC16 mod 16384 scatters keys evenly, unless you over-use one hash tag.
    Spread slots over nodeswhen you run itredis-cli --cluster rebalance evens out slot counts (optionally weighted). Redis's docs say it can't yet rebalance by looking at where the keys actually are.
    Give a new node some datawhen you run it--cluster add-node joins with 0 slots. Then --cluster reshard or rebalance moves slots to it, live.
    Take a node awaywhen you run itA primary must be emptied first (reshard its slots away). Then --cluster del-node.
    Replace a dead primaryautomaticIts replica is promoted once a majority of primaries agree it's down: cluster-node-timeout, then usually 1–2 s.
    Spread reads to replicasif the client asksA client that sends READONLY can read from replicas, accepting slightly stale data.
    Split one hot keynoA key lives in one slot on one node. Spread reads to replicas, cache it in the app, or keep several copies under different keys (not one shared tag).
    Add nodes when busynot in Redis itselfManaged services can add shards for you based on CPU or memory. Open-source Redis waits for an operator.
    6 · Slots vs. a hash ring

    Same goal as consistent hashing, different machinery

    Both avoid the disaster of hash(key) % nodes, where adding one server moves almost every key. A consistent-hashing ring and Redis's slot table both move only about 1/n of the keys.

    Think about it

    Questions to discuss with a neighbor

    1. {user42}:cart and {user42}:profile always share a slot. Why is that great for a transaction, and when could it hurt?
    2. In the simulator, add a fourth node to a 3-node cluster. What fraction of keys moved? What would have moved with hash % nodes, and why is that so much worse for a cache?
    3. Why does a crash move zero keys, while adding a node moves many?
    4. Crash a primary, then crash the replica that took over. Why does the whole cluster stop answering, even for keys on healthy nodes? (Look up cluster-require-full-coverage.) When might you turn that off?
    5. One product key gets 40% of all reads. Why won't adding nodes help? What will?
    6. Your cache is 20 GB and does 30,000 operations a second. One big node or a cluster? What number would change your mind?
