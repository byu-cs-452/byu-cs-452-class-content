Listening and Security

Redis listens on a port, and anyone who can reach that port can open a connection and send it bytes. That part is true. So why doesn't a stranger's message wreck the queue? Because connecting is not the same as being obeyed. Every message has to get through several layers, and each one asks a different question.

Six questions every message has to answer

LayerThe questionHow Redis and your project answer itIn production
1 · NetworkCan you even reach the port?A redis.io free database has a public endpoint: anyone on the internet can reach it, so every other layer has to hold. Self-hosted Redis listens only on 127.0.0.1 by default, and protected-mode refuses outside connections when no password is set.Redis sits in a private network (VPC). A firewall or security group lets in only the web and worker machines. Only the web front door is public.
2 · Encryption (TLS)Can anyone on the way read or change it?Without TLS, your password and every image cross the network in plain text. redis.io supports TLS; redis-py turns it on with ssl=True.TLS everywhere, even inside the private network.
3 · AuthenticationWho are you?Every connection must send AUTH with the right password before any other command works. Otherwise: NOAUTH Authentication required.Separate users per service, long random passwords from a secret manager, rotated.
4 · Authorization (ACL)What are you allowed to do?The default user can run every command on every key, including FLUSHALL and CONFIG. Redis 6 ACLs limit each user to certain commands, keys and pub/sub channels: NOPERM.Least privilege: the web server can only push jobs; workers can only take jobs and write results.
5 · LimitsHow much are you allowed to do?maxclients, timeouts, the largest allowed value, and output buffer limits stop a flood from taking Redis down.Rate limits and upload size limits at the front door, before anything reaches Redis.
6 · ValidationIs the data safe to use?The worker parses the job with json.loads, checks the fields and the image size, and only then decodes it. JSON is just data; it can't run code.Never pickle.loads or eval data from a queue: a crafted pickle runs code on the worker. Treat every message as untrusted, even from your own queue.
This really happens

What attackers do with an open Redis

The classic: no password, port open

Bots scan the whole internet for port 6379 all day. On a Redis with no password, an attacker can use CONFIG SET dir and CONFIG SET dbfilename to make Redis write its data file somewhere useful, like a user's ~/.ssh/authorized_keys or a cron folder, and log in to the machine.

Modern malware campaigns

Security researchers have tracked malware built for exposed Redis servers. In 2023, Aqua Security described HeadCrab, which compromised over a thousand servers by making them replicas of an attacker's server and loading a malicious module. Unit 42 described P2PInfect, a worm that spread the same way. All of them start with a Redis that anyone could reach and run commands on.

Each layer above breaks these attacks: a private network means the scanner never reaches the port, a password stops the commands, and ACLs keep even a logged-in user away from CONFIG, REPLICAOF and MODULE.

Least privilege

Give each program only the commands it needs

With ACL users, a stolen web-server password can push jobs, and that's it. It can't wipe the database, read other keys or publish fake answers.

# web front door: queue jobs, hear its own replies
ACL SETUSER web on ><long-random-password> resetkeys resetchannels ~jobs:queue &replies:* -@all +rpush +subscribe +ping

# workers: take jobs, write results, publish replies
ACL SETUSER worker on ><another-password> resetkeys resetchannels ~jobs:* ~result:* &replies:* -@all +blmove +lrem +hset +hdel +hincrby +set +publish +ping

# in Python, log in as that user over TLS
r = redis.Redis(host=HOST, port=PORT, username="web", password=os.environ["REDIS_PASSWORD"], ssl=True)

# what an attacker with the web password sees
FLUSHALL                  → (error) NOPERM ... has no permissions to run the 'flushall' command
GET result:7f3a…          → (error) NOPERM ... has no permissions to run the 'get' command
PUBLISH replies:web1 …    → (error) NOPERM ... has no permissions to run the 'publish' command

~pattern limits keys, &pattern limits pub/sub channels, +cmd / -@all limit commands. Check who you are with ACL WHOAMI and what you can do with ACL GETUSER web.

For the work queue project

Five things to fix in your own setup

  1. Get the password out of settings.py. Read it from an environment variable. A password committed to a public GitHub repo is found by bots within minutes.
  2. Turn on TLS (ssl=True) so the password and images aren't sent in plain text.
  3. Make a web user and a worker user with only the commands they need, instead of everyone using default.
  4. Validate jobs in the worker: parse JSON, check that id is a UUID and the image is the size you expect, and drop anything else.
  5. Limit uploads at the front door (Flask's MAX_CONTENT_LENGTH) so nobody can push a 2 GB "image" into Redis.
