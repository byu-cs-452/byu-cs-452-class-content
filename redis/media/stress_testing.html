Stress testing the work queue

"Stress test" sounds like it measures how much load your system can take. A test only measures its narrowest point, though, and in this project that's often not the part you think. Before trusting a number, ask what your test is really testing.

1 · Read the test first

What stress_test.py actually does

  • 20 requests, 50 ms apart, from 20 threads in one Python process on your laptop. That's a single burst of about 20 requests in one second, not sustained traffic.
  • The same 432 KB PNG (jemma.png) every time, read from disk again in each thread.
  • It measures nothing. It prints the predictions, then sleeps 300 seconds. There's no timing, no count of failures, no throughput.
  • The client, the web server, the worker and TensorFlow all share one laptop, so the load generator competes with the thing it's testing.

The surprise: each job is 0.8 MB in Redis

The web server resizes the picture to 224×224, stores it as float32 (224 × 224 × 3 × 4 bytes = 602 KB) and base64-encodes it (×4/3 → about 800 KB). A 77 KB castle JPEG becomes 800 KB of text pushed to Redis, then pulled back down by the worker.

With a free cloud Redis, every job crosses your home internet connection twice, and the 30 MB database holds only about 37 jobs at once. So the default test mostly measures your upload speed and the free tier's memory, not your queue design.

3 · A test should produce numbers

Make the stress test measure something

Read the image once, time every request, and report what a user would feel: how many requests finished per second, the median and the slow tail (p95), and how many failed.

import time, statistics, requests
from concurrent.futures import ThreadPoolExecutor

URL, N, CONCURRENCY = "http://localhost:5000/predict", 200, 20
IMAGE = open("castle_image.jpg", "rb").read()        # read once, not once per thread

def one(_):
    t0 = time.perf_counter()
    try:
        ok = requests.post(URL, files={"image": IMAGE}, timeout=60).json()["success"]
    except Exception:
        ok = False
    return ok, time.perf_counter() - t0

start = time.perf_counter()
with ThreadPoolExecutor(CONCURRENCY) as pool:        # the with-block joins every thread
    results = list(pool.map(one, range(N)))
elapsed = time.perf_counter() - start

times = sorted(t for ok, t in results if ok)
fails = sum(not ok for ok, _ in results)
print(f"{N} requests in {elapsed:.1f}s = {N / elapsed:.1f} req/s, {fails} failed")
print(f"median {statistics.median(times):.2f}s  p95 {times[int(len(times) * .95) - 1]:.2f}s  max {times[-1]:.2f}s")

Also watch the server side while it runs: LLEN image_queue (is the backlog growing?), INFO memory in Redis, and CPU in Task Manager or top. A growing queue means the worker is the bottleneck; a busy client CPU means the test itself is.

4 · Stress the system, not your Wi-Fi

Removing bottlenecks so you test what you meant to

BottleneckWhy it's thereHow to remove it for a local test
Home internetEvery job goes up to a cloud Redis and back down, 0.8 MB each way.Run Redis locally: docker run -p 6379:6379 redis:7 (or WSL). Point settings.py at localhost.
Free tier memory30 MB ÷ 0.8 MB ≈ 37 waiting jobs, then writes fail.Local Redis has gigabytes. Or shrink each job (next row).
Payload sizefloat32 + base64 makes each image 10× bigger than the JPEG.Send uint8 pixels (150 KB, ~200 KB base64), or push the original JPEG bytes and let the worker resize. Same answer, a fraction of the bytes.
One workerResNet50 on a CPU handles about 16 images per second, and the original code breaks with two workers.Fix the atomic pop (deliverable 4), then run several workers. Each needs a CPU core and about 1 GB of RAM.
Flask dev serverapp.run() is one process for development; the image preprocessing runs there too.Use a real server with several processes: gunicorn -w 4 run_web_server:app (macOS/Linux) or waitress-serve --threads 8 run_web_server:app (Windows).
Polling sleepsEvery request waits up to 0.25 s extra, and waiting requests hammer Redis with GETs.Notifications (deliverable 5). This mostly helps latency, not throughput.
The model itselfWhen you want to test the queue, the model hides everything else.Swap in a stub model (sleep 10 ms, return a fake answer) to measure just the plumbing. Then benchmark the model by itself.
The test clientSame laptop as the servers, one Python process.Watch its CPU. For more load, run the generator on another machine or use a load tool (section 5).

The habit: change one thing, re-run, compare numbers. Each fix moves the bottleneck somewhere else, and that's the point: you're learning where the limits are, one at a time.

5 · Closer to real customers

Real load tests

  • Real users don't arrive in a burst of 20. They arrive at random times (a Poisson process), pause between requests ("think time"), and send different images of different sizes.
  • Different questions, different tests: load (expected traffic, steady), stress (ramp up until it breaks; where's the knee?), spike (sudden 10× jump), soak (hours at normal load to find leaks and slow growth).
  • Fixed rate vs. fixed users. 20 users who each wait for an answer send less when the server slows down, which hides the problem. A fixed arrival rate keeps sending, like real customers do, and shows the backlog honestly.
  • Report percentiles, not averages: p50, p95, p99 latency, error rate and throughput, against a goal such as "95% of requests under 3 seconds at 30 req/s."
  • Run the load from somewhere else (another machine or the cloud), and watch the server's queue length, memory and CPU at the same time.
# locustfile.py  —  pip install locust ; locust -f locustfile.py
import random, pathlib
from locust import HttpUser, task, between

IMAGES = [p.read_bytes() for p in pathlib.Path("test_images").glob("*.jpg")]

class Customer(HttpUser):
    wait_time = between(1, 5)          # think time

    @task
    def predict(self):
        with self.client.post("/predict", files={"image": random.choice(IMAGES)},
                              timeout=30, catch_response=True) as r:
            if r.status_code != 200 or not r.json().get("success"):
                r.failure("no prediction")
// k6: a fixed arrival rate, with a pass/fail goal
export const options = {
  scenarios: { steady: { executor: "constant-arrival-rate",
    rate: 30, timeUnit: "1s", duration: "5m", preAllocatedVUs: 200 } },
  thresholds: { http_req_duration: ["p(95)<3000"], http_req_failed: ["rate<0.01"] },
};

Locust (Python) gives a live web dashboard of users, requests per second and latency percentiles. Other common tools: k6, JMeter, and the quick command-line tools hey and oha.

Think about it

Questions

  1. In the project as given, which stage is the bottleneck on your machine? How could you prove it with a measurement instead of a guess?
  2. The free Redis holds about 37 jobs. If requests arrive faster than the worker finishes them, how many seconds until writes start failing?
  3. Little's law: requests in the system = arrival rate × time each one spends there. At 20 req/s and 2 s per request, how many requests are in flight? How many open connections and threads is that?
  4. Why might a test with 20 users who wait for each answer report better numbers than real traffic at the same average rate?
  5. You added 4 workers and throughput didn't change. What does that tell you?
