Pooling Redis Subscribers

In the improved work queue design, the web front door subscribes and waits for Redis to tell it the answer is ready. If every waiting request opens its own subscriber connection, the number of connections grows with the load, and something runs out. A pooled design gives each web process one subscriber connection and sorts the incoming messages to the right request inside the process.

    How one connection serves every waiting request

    The trick is a dictionary. Each request puts a future (a placeholder for "the answer, later") in the dictionary under its id, then waits on it. One listener task owns the subscriber connection, reads each message, looks up the id, and hands the answer to that request. Requests never touch the socket.

    
    
      
  
      
  
      
    
      
      
      One subscriber per request
      

      # redis-py, inside the Flask /predict route
def predict(image):
    k = str(uuid.uuid4())
    p = r.pubsub()                  # new connection
    p.subscribe(f"result:{k}")      # before the push
    r.rpush("image_queue", json.dumps(
        {"id": k, "image": encode(image)}))
    for msg in p.listen():          # holds the socket
        if msg["type"] == "message":
            p.close()
            return json.loads(msg["data"])
      
      
      A subscribed connection can't be handed back to a connection pool, because Redis will push messages on it at any time. So every waiting request owns one socket until its answer comes.
      
    
      
    
      
      
      Pooled: one listener per process
      

      # redis.asyncio; one process, many requests
ME = f"replies:{socket.gethostname()}:{os.getpid()}"
waiters = {}                        # id -> Future

async def listener():               # started once
    p = r.pubsub()
    await p.subscribe(ME)           # ONE connection
    async for msg in p.listen():
        if msg["type"] != "message": continue
        reply = json.loads(msg["data"])
        fut = waiters.pop(reply["id"], None)
        if fut: fut.set_result(reply["preds"])

async def predict(image):
    k = str(uuid.uuid4())
    fut = asyncio.get_running_loop().create_future()
    waiters[k] = fut                # register first
    await r.rpush("image_queue", json.dumps(
        {"id": k, "reply_to": ME, "image": encode(image)}))
    try:
        return await asyncio.wait_for(fut, 30)
    finally:
        waiters.pop(k, None)
      
      
      The worker does r.publish(job["reply_to"], json.dumps({"id": ..., "preds": ...})). Each process has its own reply channel, so it only hears its own answers. (Pattern subscribing to result:* also works on one connection, but then every process hears every answer.)
      
    
      
  
      

      



      
  
      3 · Listening vs. connecting
      
  
      What a connection really is
      
  
      A TCP connection is named by four numbers: client IP, client port, server IP, server port. Redis listens on one port, 6379, and every client connection shares it. What makes each connection different is the client's side, and the client's operating system picks a temporary ephemeral port for each one it opens.
      
  
      
  
      
    
      
      
      Myth: "A server can only have 65,535 connections."
      
      
      A port number is 16 bits, so one IP address has 65,535 ports. But the server uses only one of them, 6379. Connections from different clients have different 4-tuples, so a Redis server can hold far more than 65,535 connections. The real server-side limits are open files and memory.
      
    
      
    
      
      
      Where the port limit really bites: the client
      
      
      One web host talking to one Redis address can only have as many connections as it has ephemeral ports: about 28,000 on Linux and 16,000 on Windows and macOS. Closed connections also sit in TIME_WAIT for 30 to 120 seconds before their port can be reused. Opening a fresh subscriber per request burns through ports fast. A pool opens one.
      
    
      
  
      

      



      
  
      4 · Subscriber limits inside Redis
      
  
      What Redis itself will and won't put up with
      
  
        
    
      • maxclients, 10,000 by default. Past it, a new connection gets ERR max number of clients reached. Redis needs one file descriptor per client plus about 32 for itself, so if the OS gives it fewer (ulimit -n), it lowers maxclients on its own and logs a warning at startup.
        • 
    
      • Every client costs memory: a client struct, a query buffer and an output buffer. It's small per connection, but 100,000 idle subscribers is real RAM. Check with INFO clients and CLIENT LIST.
        • 
    
      • Slow subscribers get kicked. The default client-output-buffer-limit pubsub 32mb 8mb 60 disconnects a subscriber that falls 32 MB behind, or stays more than 8 MB behind for 60 seconds. With a pool, one connection carries every request's answers, so the listener must read fast and never do slow work itself. It hands answers off and goes back to reading.
        • 
    
      • Pub/sub is fire and forget. If nobody is subscribed when the worker publishes, the message is gone. That's why the request registers (and the listener is subscribed) before the job is pushed. If the pooled connection drops, re-subscribe and fall back to a stored result key for anything in flight.
        • 
    
      • Subscribing is cheap; connecting is not. One connection can subscribe to thousands of channels. The expensive part is the TCP connection (handshake, socket, file descriptor, buffers), not the channel.
        • 
    
      • Clusters: a classic PUBLISH in Redis Cluster is broadcast to every node. Redis 7 added sharded pub/sub (SSUBSCRIBE / SPUBLISH) so a channel lives on one shard, like a key.
        • 
  
      

      



      
  
      5 · It depends on the operating system
      
  
      Listening and subscribing on Linux, Windows and macOS
      
  
      Typical defaults. They change between versions and distros, so check yours with the command shown.
      
  
      
    
      
      
      LimitLinuxWindowsmacOS
      
      
        
      Open sockets per process
          Each socket is a file descriptor. Soft limit is often 1,024 (ulimit -n). Raise it with ulimit -n, /etc/security/limits.conf, or LimitNOFILE= in a systemd unit.
          Sockets are kernel handles, with no small per-process cap (millions of handles). Memory runs out first.
          Shells often start at 256 (ulimit -n). The ceiling is sysctl kern.maxfilesperproc.
      
        
      Ephemeral ports (outgoing connections)
          32768–60999, about 28,000. sysctl net.ipv4.ip_local_port_range
          49152–65535, about 16,000. netsh int ipv4 show dynamicport tcp
          49152–65535, about 16,000. sysctl net.inet.ip.portrange.first net.inet.ip.portrange.last
      
        
      TIME_WAIT after a close
          60 seconds, built into the kernel.
          Up to 120 seconds by default (registry TcpTimedWaitDelay).
          About 30 seconds (2 × net.inet.tcp.msl).
      
        
      Listen backlog (connections waiting to be accepted)
          net.core.somaxconn: 4,096 on kernels since 5.4 (128 before).
          SOMAXCONN gives a few hundred; SOMAXCONN_HINT(n) asks for more.
          kern.ipc.somaxconn: 128.
      
        
      Ports below 1024
          Need root or CAP_NET_BIND_SERVICE.
          No privileged ports, but the firewall asks, and Hyper-V, WSL or Docker can reserve whole ranges, so binding fails with "access denied". Check with netsh int ipv4 show excludedportrange protocol=tcp.
          Any user can bind them since macOS 10.14 (Mojave).
      
        
      Sharing a port
          SO_REUSEPORT lets several processes listen on one port, and the kernel spreads connections across them.
          SO_REUSEADDR lets another program take over a port you're using. Use SO_EXCLUSIVEADDRUSE to prevent that.
          SO_REUSEPORT exists, but it doesn't spread the load the way Linux's does.
      
        
      Waiting on many sockets at once
          epoll: scales to hundreds of thousands of connections. Redis uses it.
          IOCP scales well. Plain select() is capped (64 sockets by default in C, 512 in Python).
          kqueue: scales well. Redis uses it.
      
        
      Running Redis itself
          Native, and where Redis runs in production.
          No native Redis. Run it in WSL2 or Docker.
          Native (brew install redis). Fine for development.
      
            
    
      
  
      
  
      Takeaway: on every OS, opening one connection per waiting request hits a wall in the thousands, whether that's file descriptors, ephemeral ports or maxclients. Pooling turns "one connection per request" into "one connection per process," and the walls go away.
