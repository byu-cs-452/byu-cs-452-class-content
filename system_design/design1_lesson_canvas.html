1. One-to-many

One row on the "one" side relates to many rows on the "many" side. This is the relationship you'll use most.

The rule: the foreign key lives on the many side. Always. One author has many books, so book carries author_id.

CREATE TABLE author (
    author_id INT PRIMARY KEY,
    name      VARCHAR(100)
);

CREATE TABLE book (
    book_id   INT PRIMARY KEY,
    title     VARCHAR(200),
    author_id INT NOT NULL,          -- FK on the MANY side
    FOREIGN KEY (author_id) REFERENCES author(author_id)
);

If you ever find yourself putting a list into a column (book_ids VARCHAR(500) holding "3,17,42"), that is a one-to-many asking to be a foreign key. It's also a 1NF violation.

Ask yourself two questions, one per direction. "Can one author have many books?" and "Can one book have many authors?" You need both answers before you can draw the line. Getting the second one wrong is what turns a one-to-many into a missed many-to-many.

Then ask whether it's optional. Must every book have an author? Can an author exist with no books? That's participation, and it decides whether the foreign key is NOT NULL.

In the homework: cars have multiple tires, and a tire belongs to exactly one car. Which table gets the foreign key? And can a tire exist in your model before it's installed on anything?

2. Many-to-many

Many rows on each side. A relational database cannot store this in two tables, so you add a third: a junction (or bridge) table holding a foreign key to each side.

CREATE TABLE student (student_id INT PRIMARY KEY, name VARCHAR(100));
CREATE TABLE course  (course_id  INT PRIMARY KEY, title VARCHAR(100));

CREATE TABLE enrollment (
    student_id INT,
    course_id  INT,
    PRIMARY KEY (student_id, course_id),      -- composite key: no duplicate pairs
    FOREIGN KEY (student_id) REFERENCES student(student_id),
    FOREIGN KEY (course_id)  REFERENCES course(course_id)
);

Notice that a many-to-many is really two one-to-manys pointing at the junction table.

The part people miss: the junction table usually wants attributes of its own. Enrollment isn't just a pairing, it has a grade, a term, and a date. The moment the relationship carries facts, it has become an entity in its own right (your book may call it an associative entity), and it deserves a real name.

CREATE TABLE enrollment (
    student_id INT,
    course_id  INT,
    term       VARCHAR(20),
    grade      CHAR(2),
    PRIMARY KEY (student_id, course_id, term)  -- now they can retake it
);

That primary key change is a design decision with teeth. Ask what makes a row unique, and you'll usually find a hidden requirement.

In the homework: mechanics work at more than one garage, and cars can have multiple owners. Both are many-to-many. What would you want to record about each pairing? For ownership, does it matter when it started and ended, or that someone used to own the car?

3. Supertype and subtype

Use this when several kinds of thing share most of their attributes but differ in a few. The shared attributes go on the supertype, and the distinct ones go on each subtype.

Two questions define the shape:

  • Disjoint or overlapping? Can one row be two subtypes at once? Disjoint means no, overlapping means yes.
  • Total or partial? Must every supertype row be some subtype, or can it be only the general thing?

Three ways to implement it. Each is defensible, and you should be able to say why you picked yours:

ApproachHowGoodBad
One table for everything
(single table inheritance)		 All attributes in one table plus a type column. Unused columns are NULL. No joins. Simple queries. Lots of NULLs. The database can't enforce "mechanics must have a salary".
A table per subtype
(table per concrete class)		 No supertype table. customer and mechanic each repeat the shared columns. No NULLs, no joins. Shared columns are duplicated, and nothing can reference "a person" generically. Breaks badly if one row must be both.
Supertype plus subtype tables
(class table inheritance)		 person holds the shared columns. customer and mechanic each have a PK that is also a FK to person. No duplication, no NULLs, other tables can point at person, and one person can be both. Joins to assemble a whole record.

The third pattern is what the homework asks for when it says customers and mechanics "should be sub-entities of a larger person table":

CREATE TABLE person (
    person_id  INT PRIMARY KEY,
    first_name VARCHAR(50),
    last_name  VARCHAR(50)
);

CREATE TABLE mechanic (
    person_id INT PRIMARY KEY,                -- PK and FK at the same time: 1-to-1 with person
    salary    DECIMAL(10,2) NOT NULL,
    FOREIGN KEY (person_id) REFERENCES person(person_id)
);

Making the subtype's primary key also a foreign key is the trick that enforces one subtype row per person.

In the homework, read this sentence very carefully: "Discount Tire has customers and mechanics (who may bring in their cars for repairs)," and then this question from the list: "How many mechanics get their tires from Discount Tire?" What do those two together tell you about whether your subtypes are disjoint? Which of the three approaches above survives that requirement, and which quietly breaks? Also: we track birthdays for customers but not mechanics, and salary for mechanics but not customers. Where does each attribute go?

4. The trap that costs the most points

There are two different kinds of fact in this domain, and they need different structures:

  • State: what is true right now. Which tires are on the car, the current tread depth, the last rotated date.
  • Event: what happened, with a date attached. This tire was purchased here on this date, this car was rotated on these six occasions, this person owned this car during this period.

A model that stores only current state cannot answer a question about history. Look at the question list with that in mind:

  • "What is the total number of tires a customer has bought?" — can you still answer this after the tire is replaced and thrown away?
  • "How many cars has a customer brought in?" — owning a car and bringing it to a garage are different facts. Does your model have both?
  • "How many tires are installed on the customer's birthday?" — which table holds the install event, and does it know who was being served?
  • "Which garages can handle five customers at the same time?" — this one is answerable from a plain attribute. Which one, and do you have it?

You don't have to model every event in the world. You do have to make a deliberate choice, and be able to say which questions your model answers and which it doesn't.

5. A few smaller decisions

  • Addresses in their own table (the homework requires it). So: do two people at the same house share one address row, or get one each? Your answer changes whether person-to-address is many-to-one or many-to-many. Both are defensible; think about what happens when Smarty corrects a shared row.
  • Derived and dependent data. City and state are determined by zip code. Storing all three is a 3NF conversation. Storing a tire's age instead of its install date is the same mistake in a smaller package: store the fact, derive the rest.
  • Natural versus surrogate keys. A tire has a unique barcode. Is that your primary key, or do you add a tire_id anyway? Argue both sides. What happens when a barcode is misprinted or reused?
  • Multi-valued attributes. One person, several phone numbers. phone1, phone2, phone3 is the wrong answer, and knowing why is most of 1NF.
  • Name your relationship lines with verbs. "Mechanic works at garage" reads back as a sentence you can check against the requirements. Unlabeled lines hide wrong assumptions.

6. In-class activity

Work on your own diagram in drawsql.app or whatever tool you like.

  1. Inventory your relationships. List every line in your diagram and label it 1:1, 1:M, or M:N. For each, say the sentence out loud in both directions.
  2. Pick three questions from the homework's question list. For each, write the join path through your tables: customer → owns → car → tire. If you get stuck, that's a missing table, not a missing query.
  3. Trade with a partner and run the checklist below on their diagram. Finding someone else's missing junction table is much easier than finding your own.

Checklist before you submit

  • Every entity has a primary key, and every relationship is carried by a foreign key.
  • No many-to-many line is drawn directly between two entities. Each one has a junction table.
  • Every junction table has been asked whether it needs attributes of its own.
  • Person, customer, and mechanic are structured so that a person can be both, if you decided that they can.
  • No repeating groups (phone1, phone2), and no comma-separated lists in a column.
  • Each attribute sits on the entity it actually describes, and is not duplicated on another.
  • You can trace a join path for every question in the homework's list, or you can say why you chose not to support one.
  • Exported as a PDF, which is what the submission requires.
