1. One-to-many

The rule: the foreign key lives on the many side. One author has many books, so book carries author_id.

CREATE TABLE book (
    book_id   INT PRIMARY KEY,
    title     VARCHAR(200),
    author_id INT NOT NULL,          -- FK on the MANY side
    FOREIGN KEY (author_id) REFERENCES author(author_id)
);

A list stuffed into a column (book_ids holding "3,17,42") is a one-to-many asking to be a foreign key.

Say the sentence in both directions. "Can one author have many books?" and "Can one book have many authors?" You need both answers before you draw the line; skipping the second is how a many-to-many gets missed. Then ask whether it's optional, which decides NULL or NOT NULL.

Tire shop: cars have multiple tires, a tire belongs to one car. Which table gets the FK? Can a tire exist before it's installed?

2. Many-to-many

Many on each side. Two tables can't hold that, so a third carries a foreign key to each:

CREATE TABLE enrollment (
    student_id INT,
    course_id  INT,
    PRIMARY KEY (student_id, course_id),      -- composite key: no duplicate pairs
    FOREIGN KEY (student_id) REFERENCES student(student_id),
    FOREIGN KEY (course_id)  REFERENCES course(course_id)
);

A many-to-many is really two one-to-manys pointing at the middle table.

It goes by many names. junction, bridge, join, link, cross-reference (xref), intersection, mapping, association table; associative or composite entity; pivot table (Laravel); through model (Django, Rails). Same structure, different vocabulary. When an interviewer uses a word you haven't heard, this is usually it.

The part people miss: the table usually wants attributes of its own. Enrollment isn't just a pairing, it has a term and a grade. Once a relationship carries facts it's an entity, and it deserves a real name and a rethought key:

PRIMARY KEY (student_id, course_id, term)   -- now they can retake it

Asking "what makes a row unique?" almost always surfaces a hidden requirement.

Tire shop: mechanics work at multiple garages, cars have multiple owners. What would you record about each pairing? Does it matter when someone stopped owning the car?

3. Supertype and subtype

Several kinds of thing share most attributes and differ in a few. Two questions define the shape:

  • Disjoint or overlapping? Can one row be two subtypes at once?
  • Total or partial? Must every supertype row be some subtype?
ApproachGoodBad
One table, plus a type column No joins. NULLs everywhere; can't enforce "mechanics have a salary".
A table per subtype, shared columns repeated No NULLs, no joins. Duplication; nothing can reference "a person"; breaks if a row must be both.
Supertype + subtype tables, subtype PK is also an FK No duplication, no NULLs, others can point at person, one person can be both. Joins to assemble a record. 
CREATE TABLE mechanic (
    person_id INT PRIMARY KEY,                -- PK and FK at once: 1-to-1 with person
    salary    DECIMAL(10,2) NOT NULL,
    FOREIGN KEY (person_id) REFERENCES person(person_id)
);

Tire shop: mechanics "may bring in their cars for repairs," and one question asks how many mechanics buy their tires here. So are the subtypes disjoint? Which approach above survives that, and which quietly breaks? We track birthdays for customers only, salary for mechanics only — where does each attribute live?

4. State versus event

Two different kinds of fact, and they need different structures:

  • State: what is true now. Which tires are on the car, current tread, last rotated date.
  • Event: what happened, with a date. This tire was bought here, this car was rotated on these six occasions, this person owned this car during this period.

A model that stores only current state can never answer a question about history, and you usually discover this a year after launch, when someone asks for a trend. Check it against the questions in the prompt:

  • "Total tires a customer has bought" — still answerable after the tire is replaced and thrown away?
  • "How many cars has a customer brought in?" — owning a car and bringing it in are different facts. Do you have both?
  • "Tires installed on the customer's birthday" — which table holds the install event, and does it know who it was for?

Not every event needs modeling. But choose deliberately, and be able to say which questions your model answers and which it can't.

5. Details worth discussing

  • Shared addresses. Do two people at one house share an address row or get their own? That changes person-to-address from many-to-one to many-to-many. Consider what happens when address verification corrects a shared row.
  • Derived data. Zip determines city and state. Store the fact, derive the rest — the same reason you store an install date, not an age.
  • Natural versus surrogate keys. A tire has a unique barcode. Is that your primary key, or do you add tire_id anyway? What happens when a barcode is misprinted or reused?
  • Multi-valued attributes. One person, several phone numbers. phone1, phone2, phone3 is the wrong answer, and knowing why is most of 1NF.

6. Let's start working on it!

Open drawsql.app or your tool of choice and we'll start the tire shop model together. Then, on your own or with a partner:

  1. Label every line 1:1, 1:M, or M:N, and say each one out loud in both directions.
  2. Pick three questions from the prompt and trace the join path: customer → owns → car → tire. Where you get stuck is a missing table, not a missing query.
  3. Trade diagrams. Spotting someone else's missing junction table is far easier than spotting your own.

Questions worth asking of any model you build

Not a grading rubric — a habit. These are the same questions a good reviewer will ask you at work:

  • Does every entity have a key, and does every relationship ride on a foreign key?
  • Is any many-to-many drawn as a direct line, with no table in the middle?
  • Does each middle table need attributes of its own?
  • Does each attribute live on the thing it actually describes, exactly once?
  • Which questions can this model never answer, and am I at peace with that?
