Where logs live in production

Pushing log lines to a Redis list works fine for a class project. In production, logs are huge, written all the time and rarely read, so teams use systems built for exactly that. Here is what they look like.

[Page created using Claude by Professor Reynolds]

Why not Redis?

Redis is the wrong shape for logs

  • It keeps everything in RAM. A busy service writes gigabytes of logs a day. Keeping 30 days of that in memory costs far more than compressed files on disk or in object storage.
  • It can't search inside the text. "Every error mentioning image 7f3a… in the last hour" means reading the whole list.
  • A list grows forever unless you cap it, and capping it (LTRIM, or XADD … MAXLEN) throws away old logs exactly when you need to look back.
  • Logs and work share one server. A flood of log writes slows down the queue it's supposed to be watching.

Redis does have a good logging role: a short, capped buffer of recent events (a Redis Stream with MAXLEN) for a live dashboard.

Habits that carry over

What to do in any of them, including your project

  • Structured logs: one JSON object per line, with the same field names everywhere.
  • A request id on every line. The project's UUID is perfect: put it in the web server's and the worker's log lines, and one search shows a request's whole story across machines.
  • Levels (DEBUG, INFO, WARN, ERROR) so you can keep errors for a year and debug chatter for a day.
  • Never log secrets (passwords, tokens like your Redis password) or personal data you don't need.
  • Logs, metrics and traces are three different tools. Counting requests per second is a metric (Prometheus), not a log search. OpenTelemetry is the standard way to emit all three.
